# Spike: ACM Search traversal semantics for #2661 (DD-FLEET-017 D4 source adapter)

> **Re-scope note (2026-11-18, same day):** #2661 was re-scoped from `AF → ACM`
> to `AF → FMC`, with ACM Search as an FMC source adapter (DD-FLEET-017 v2).
> Every finding below still holds and now governs the **collector at sync time**
> (DD-FLEET-017 v2 §5 D4), not an AF request path.

**Date**: 2026-11-18
**Cluster**: `kubernaut492-sno-b` (SNO-b, helios08 lab), ACM **2.17.4**,
MultiClusterHub `2.17.4/2.17.4`,
`acm-search-v2-api-rhel9@sha256:85c53e64f719b91a91c1eaed06111e0c9eefe27d7f62e4114568bfe5b141a3ac`.
**Endpoint**: `https://search-spike-2592-open-cluster-management.apps.kubernaut492-sno-b.redhat-internal.com/searchapi/graphql`
(reencrypt route retained from the #2592 spike).
**Purpose**: answer the traversal gate — *is a keyset (`uid >`) continuation
supported, so traversal can be stable under index mutation?* — and capture
`orderBy`/`offset` behavior and the schema source for the vendored SDL.
**Scope**: read-only GraphQL queries. No Search, ACM or Kubernetes state was
modified. One temporary principal was created and removed inside the same run
(see "Principal").

## Method

Queries were sent over HTTPS with a bearer token for a temporary
least-privilege-ish principal. The GraphQL document is the adapter's own
`SearchQuery` shape (`search(input:) { count items }`), with `filters`,
`limit`, `offset` and `orderBy` varied per probe. Item fields inspected:
`_uid`, `cluster`, `namespace`, `name`.

### Principal

`ServiceAccount open-cluster-management/dd2661-probe` with
`ClusterRoleBinding dd2661-probe-view → ClusterRole view` (cluster-wide read),
minted a 15-minute token, then both objects were deleted in the same shell
(`CLEANUP: sa+binding removed`). Visibility behavior matched the recorded
#2592/#2593 evidence: the same queries against `search-collector-sa` (which
holds cluster-wide namespace read) returned **count=0** — an empty result is
not evidence of absence.

Note: DD-FLEET-011 recorded that Search kept returning a removed principal's
resource for 31.06 s after the binding was removed. The temporary principal is
therefore expected to stay visible to Search briefly after this run; it holds
no credentials after token expiry.

- `count` returns the **total** matched records when `items` are requested

## Mutation probe (2026-11-18, second run): does offset skip defeat the guards?

Purpose: quantify the residual now recorded in DD-FLEET-017 v2 §5 D4.3 — an offset walk over a
mutating index. Fixture: namespace `dd2661-walk` / `dd2661-walk2`, 300
ConfigMaps (302 visible including the namespace's system ConfigMaps), chunk 25,
`orderBy: "uid asc"`, same hub/build/route. Mutations were issued with
`kubectl` after page 2 of a walk; the walk then continued to the end.

| Case | Mutation | Result |
|---|---|---|
| Baseline | none | 13 pages, 302 items, `count` stable at 302, 1.82 s |
| A | delete 10 items **already passed** by the cursor | `count` 302 on pages 1–5 then **292** on pages 6–13; items 292; duplicates 0; **4 items silently skipped** (`cm-051`, `cm-100`, `cm-103`, `cm-126`); `sum(items) == count` was **true** |
| B | create 10 items after page 2 | `count` stable at 292, items 292, duplicates 0, none of the created items appeared (not yet indexed) |
| C | delete 5 already-passed **and** create 5 after page 2 | `count` stable at 302 for all 13 pages, duplicates 0, skipped 0, created items seen 0 — neither mutation became visible inside the 1.8 s walk (index settle lag that run: 6.5 s) |

Index settle lag observed: 0.9 s and 6.5 s for 300 creates; a delete issued
mid-walk became visible roughly 0.4 s later. Lag is therefore comparable to or
longer than a walk at this size.

### Verdict

1. **Offset skip is real**, not theoretical: four resources were lost from a
   completed-looking walk, and `sum(items) == count` still held. That guard is
   **not** a skip detector — it only detects a malformed response. DD-FLEET-017 v2
   D4 is corrected accordingly.
2. **Count stability is the effective detector** for the delete-shift shape: the
   302→292 transition was visible on the next page and would trigger the
   bounded restart.
3. When `count` is unstable the recovery must be a **fresh walk from offset 0**;
   the restart is validated by construction and remains to be proven by
   `UT-FMC-SRC-2661-015`.
4. **Balanced delete+create** (equal counts, mutually cancelling offsets) can
   in principle defeat both guards. It could not be induced here because index
   lag exceeded the walk duration, so it remains an unproven, low-probability
   blind spot — documented, not excluded. Keyset continuation (T-A) is the only
   design that removes it, and it is unavailable on this build.
5. Practical bound: exposure is the walk duration (≈2 s at 300 identities,
   ≈1 s at page cadence) versus index lag (≥0.4 s, up to 6.5 s). Larger
   fixtures lengthen the walk and widen the window, which is why the
   working-set cap and the restart rule matter more than the page size.


## Label-projection probe (2026-11-18, third run)

Question raised by review: ACM Search projects labels as a semicolon `label`
field — is it **complete** for workload kinds, and what does a missing key mean?

Method: compare Search's `label` value against the Kubernetes object's real
labels for sampled objects on the hub (read-only, same route/principal).

| Object | k8s labels | projected | missing | `label` key present |
|---|---|---|---|---|
| Pod `openshift-etcd/etcd-…` | 4 | 4 | none | yes |
| Pod `openshift-etcd/installer-1-…` | 1 | 1 | none | yes |
| Pod `openshift-etcd/installer-2-…` | 1 | 1 | none | yes |
| Namespace `openshift-etcd` | 5 | 5 | none | yes |
| ConfigMap `…/kube-root-ca.crt` (no labels) | 0 | 0 | none | **no** |

Verdict: the projection is complete for the sampled labeled workloads, and a
**missing `label` key means the object has no labels at all** (confirmed against
kubectl), so mapping it to "absent" is correct rather than a silent under-report.
Limits: 5 objects, one hub, low label cardinality; objects with very large label
sets and CRDs were not sampled. Filename-safe labels (`kubernaut.ai~1managed`)
were not observed; the existing key fallbacks remain untested against a live
object.


## S1 — proof-once page read over the real cache keyspace (2026-11-18, fourth run)

Purpose: close the increment-1 design forks before any production code — can a
page be read atomically under **one** fenced proof, what does enumeration cost,
and does per-item namespace resolution multiply the round trips?

Method: native `valkey-server` on helios08 (no cluster, no container), seeded
with the **real** key layout taken from `fmc_v2_atomic.lua` (status hash,
per-record hashes with the 15 committed fields, live index ZSET with
`score = expires_at_ms`, `member = public_id`), then prototype scripts executed
over a raw RESP client. The production script was loaded with `SCRIPT LOAD` for
the baseline. No repository code and no production service was involved.

### Correctness results

| Case | Result |
|---|---|
| Header validates the proof once and returns live-index ids | `ok`, 10 ids |
| A **staged** index containing bogus ids exists during the read | Not returned — staged state stays invisible |
| Generation mismatch | `missing` (fail closed) |
| Status TTL shortened under its claimed expiry | `ERR TTL_MISMATCH` |
| One record expired inside an otherwise valid proof | Page returns `missing` — a single bad record fails the whole page, never a partial set |

### Measurements (localhost Valkey, median of 5)

| Operation | Payload | Time |
|---|---|---|
| Header, 10 ids | 0.6 KiB | 0.27 ms |
| Header, 100 ids | 6.1 KiB | 0.94 ms |
| Header, 1 000 ids | 60.5 KiB | 6.8 ms |
| Header, 10 000 ids (cap) | 605 KiB | 84 ms |
| Page read: 100 records + 5 namespace records + proof | — | 2.95 ms |
| Page read: 50 records + 5 namespaces + proof | — | 1.18 ms |
| Baseline: 100 × single-record `read_verified` (real script) | — | 16.8 ms |
| Identity list (ids + g/v/kind/ns/name) for `SortResources` ordering, 1 000 | 85 KiB | 31 ms |
| Identity list, 10 000 | 858 KiB | **284 ms** |

### Design conclusions

1. **Atomic page read works** as two fenced calls: a *header* call validates the
   status proof once and snapshots the identity set of one generation; a *page*
   call re-validates the same fence/generation and returns only the page's
   records. A rotation between the calls fails closed (`missing`) instead of
   mixing generations — proven by the generation-mismatch case.
2. **N+1 is eliminable**: namespace records needed for inheritance ride in the
   same page call (5 extra ids measured at ≈0 cost), so a page is 2 Redis calls
   regardless of how many unlabeled resources need namespace resolution.
3. **Staged state is safely invisible** to both calls, which is what the page
   requires during a repair window.
4. **A single expired/inconsistent record fails the page closed.** Correct for
   "no unproven rows", and it maps to `unavailable` (proof/TTL inconsistency),
   not to `partial`.
5. **Ordering is the only open fork.** `inventory.SortResources` needs
   g/v/kind/ns/name for every id before slicing, which costs **284 ms and
   858 KiB at the 10k cap on every page request** — rejected. Two viable
   options:
   - **(B) order by canonical ID** for FMC pages: header (84 ms at the cap,
     0.94 ms at 100) + page read; no schema change; deterministic and unique;
     diverges from the local reader's `SortResources` order.
   - **(C) add a lexicographic identity index** maintained by the commit script:
     O(page) reads at any size (~3 ms), but it changes the tested atomic commit
     contract and needs a backfill/fallback story for existing partitions.
6. **The 10k ceiling is usable but not free**: 84 ms and 605 KiB for the header
   at the cap. Raising the ceiling without (C) multiplies that linearly.


## S2 — lexicographic identity index for ordering and filtering (2026-11-18, fifth run)

Purpose: validate option C (D2.5a) before committing to it — byte ordering of the
composed key, exact prefix ranges, cursor behaviour, and cost at the 10 000-item
cap. Native `valkey-server` on helios08, 10 000 synthetic identities across 8
namespaces (including the empty namespace), 4 kinds and 3 group/versions.

| Check | Result |
|---|---|
| 10 000 composed members (`ns \x00 kind \x00 group \x00 version \x00 name \x00 id`) | byte-sorted = **true** |
| NUL separator round-trip | intact |
| Prefix `namespace=ns-c` | **1 250 returned, 1 250 expected** |
| Prefix `namespace+kind` | mechanically correct (fixture had no intersecting pair — a fixture artifact, verified by the namespace count) |
| Cursor as exclusive range `(lastMember` | next page strictly after the cursor |
| First page (100) at 10k | **0.20 ms** |
| Next page via cursor at 10k | **0.20 ms** (no offset drift) |
| Filtered page `namespace=ns-c` (100) at 10k | **0.20 ms** |

Comparison at the cap: 0.20 ms per page and flat, versus 84 ms header + Go sort
(option B) and 284 ms identity-enumeration (rejected). Cursor stability comes
from the exclusive member range, so paging never depends on an offset that a
concurrent commit could shift.

**Conclusion:** option C is viable and cheap on the read side. What remains
unproven is only the **commit-side** change (writing the lex members in the same
staged generation and swapping both indexes atomically) — mechanical, but it
touches the DD-FLEET-016 path that must be re-qualified.


## S2b — commit path with the lex index, three cases plus a negative (2026-11-18, sixth run)

Purpose: exercise the *write* path — the only part S2 left unproven. Method: the
production `fmc_v2_atomic.lua` was patched **in a scratch copy** (repository
untouched) to write and swap a second index, then driven through the real
operations on native Valkey: `begin → repair_reconcile × N → commit`, plus
`begin → abandon_staging → begin → commit` and
`begin → repair_finalize_empty → commit`.

| Case | Assertions | Result |
|---|---|---|
| Normal commit (5 records, mixed namespaces) | commit ok; both indexes = 5; staged keys gone; status clean; page returns 5 in namespace-first order; `read_verified` for a single record still works | **PASS** |
| Abandoned staging → new begin → commit (2 records) | staging marked `uncertain`; replacement reuses the committed generation (2→2, correct); staged lex cleared by `begin`; final data/lex = 2; **no member from the abandoned generation survived** | **PASS** |
| Empty partition | `repair_finalize_empty` then empty commit ok; both indexes deleted; status clean with `empty_verified=1`; page reports zero members | **PASS** (after the refinement below) |
| Negative: lex and data indexes disagree | commit rejected with `ERR LEX_COUNT_MISMATCH`, no partial publish | **PASS** |

**Two refinements this run produced (now in D2.4/D2.5a):**

1. **A proven-empty partition has no indexes.** The first version of the page
   read treated a missing index as `missing`, which would have made every
   legitimate empty fleet read `unavailable`. Empty must be derived from the
   proof (`empty_verified=1`, `observed_count=0`), never from index presence.
2. **Disagreement is the writer's problem, not the reader's.** A commit whose
   lex member count differs from the data index is rejected
   (`LEX_COUNT_MISMATCH`), and `begin` clears an abandoned staging's lex index so
   residue can never reach a live page.

Not covered here: the Go plumbing (store interface, fakes, route, tests) and the
availability evidence under real repair windows (DD-FLEET-016 re-qualification).

## Decision

- **T-A (keyset traversal): NO.** No keyset predicate on `uid`/`_uid` is
  supported; the filter is accepted and silently matches nothing, which would
  make a paging adapter return truncated results as if complete.
- **T-B (offset traversal): YES**, with mandatory guards (DD-FLEET-017 v2 §5 D4):
  explicit `orderBy: "uid asc"`, strict `_uid` increase per page, duplicate
  detection, per-page `count` stability, final short page, and
  `sum(items) == count` at the end; any deviation fails closed to `partial`.
- **SDL refresh source**: deployed introspection is disabled, so the vendored
  SDL must be refreshed from the upstream release matching the deployed image
  digest above, not from introspection.

## Limitations (explicitly not proven)

- One SNO hub, small fixtures (88 namespaces, 232 pods), short walks of 5–9
  pages completed within seconds — this is not a scale or latency result.
  Scale evidence remains the recorded 1050-item / 11-page run.
- The concurrent-mutation probe (above) used 300 identities and one mutation
  shape per walk; it did not attempt randomized interleavings or multi-cluster
  fixtures. Offset continuation is **not** a snapshot, and the balanced
  delete+create case remains an unproven blind spot.
- The probe principal is not the production Console reader identity; #2592
  already qualified Search visibility for the scoped ServiceAccount. This
  spike answers query semantics only.
- No claim is made about other ACM 2.17.x patch levels or other Search builds.
