Rego policies are required and must be provided at install time:

  --set-file signalprocessing.policies.content=path/to/policy.rego
  --set-file aianalysis.policies.content=path/to/approval.rego

  --set signalprocessing.policies.existingConfigMap=my-sp-policy

For reference policies, see: https://github.com/jordigilh/kubernaut-demo-scenarios

=== Monitoring ===

Kubernaut is designed to work with kube-prometheus-stack.
If deployed, configure AlertManager to send alerts to the Gateway:

  receivers:
    - name: kubernaut
      webhook_configs:
        - url: "http://gateway-service.{{ .Release.Namespace }}.svc.cluster.local:8080/api/v1/signals/prometheus"
          send_resolved: true
          http_config:
            bearer_token_file: /var/run/secrets/kubernetes.io/serviceaccount/token
{{- if or (not (include "kubernaut.monitoring.prometheus.enabled" .)) (not (include "kubernaut.monitoring.alertManager.enabled" .)) }}

IMPORTANT -- monitoring.prometheus/alertManager integration is OFF by default
(separate from the webhook wiring above, which only covers Kubernaut
*receiving* alerts). This is a real cost to remediation quality, not just an
optional integration -- KubernautAgent investigates with fewer live signals,
and EffectivenessMonitor cannot fully confirm whether remediations worked.
The chart does not deploy or auto-discover Prometheus/AlertManager -- point
it at your own. Without this:
{{- if not (include "kubernaut.monitoring.prometheus.enabled" .) }}
  - EffectivenessMonitor cannot score metric-based remediation effectiveness (BR-EM-002).
  - KubernautAgent's RCA loses its Prometheus MCP investigation tool.
  - APIFrontend's severity triage falls back to its non-Prometheus default.
{{- end }}
{{- if not (include "kubernaut.monitoring.alertManager.enabled" .) }}
  - EffectivenessMonitor cannot confirm whether the triggering alert actually
    resolved after a remediation (BR-EM-002 alert-resolution scoring).
  - KubernautAgent's RCA loses its AlertManager MCP investigation tool.
{{- end }}

To enable:

  --set monitoring.prometheus.enabled=true --set monitoring.prometheus.url=http://<prometheus-host>:9090
  --set monitoring.alertManager.enabled=true --set monitoring.alertManager.url=http://<alertmanager-host>:9093
{{- end }}

=== Optional: Ecosystem RBAC for Owner-Chain Resolution (Issue #1069) ===

Gateway and EffectivenessMonitor bind to the built-in `view` ClusterRole for
owner-chain resolution, which automatically covers "well-behaved" operators
that publish `rbac.authorization.k8s.io/aggregate-to-view: "true"` (cert-manager,
Istio, KubeVirt, etc.). It does NOT cover OLM (Subscription/ClusterServiceVersion)
or other ecosystem CRDs that manage their own RBAC without aggregating to view.
If your cluster runs OLM-managed operators (or similar) under Kubernaut's
remediation scope, owner-chain resolution for resources they own will hit RBAC
Forbidden errors and silently truncate the chain.

No additionalClusterRoleBindings are configured (the default). To grant access
to a specific ecosystem, create a narrowly-scoped ClusterRole and reference it
by name -- no Kubernaut upgrade required:

  --set global.additionalClusterRoleBindings[0]=my-olm-reader

See the chart README's "Extending owner-chain-resolution RBAC" section for a
full ClusterRole example and per-service override options.

=== Upgrading ===

CRDs are NOT upgraded automatically by `helm upgrade`. To update CRDs:

   helm pull oci://quay.io/kubernaut-ai/charts/kubernaut --version <new-version> --untar
   kubectl apply --server-side --force-conflicts -f kubernaut/crds/

Run this BEFORE `helm upgrade` when CRD schemas have changed between versions.

{{- if eq $tlsNotesV.mode "hook" }}
TLS mode: hook (self-signed certificates via Helm hooks).
Certificates are automatically renewed during upgrade if they expire within 30 days.
{{- else if eq $tlsNotesV.mode "cert-manager" }}
TLS mode: cert-manager (certificates managed by cert-manager).
The authwebhook-cert Certificate resource provisions the authwebhook-tls Secret.
The datastorage-signing-cert Certificate resource provisions DataStorage's AU-9
audit-signing key (#334). A dedicated internal CA (kubernaut-interservice-ca,
DD-PLATFORM-001) auto-provisions inter-service mTLS: gateway-tls, datastorage-tls,
kubernautagent-tls, and the inter-service-ca ConfigMap. cert-manager handles
renewal automatically for all of these.
{{- else if eq $tlsNotesV.mode "manual" }}
TLS mode: manual (user-managed certificates).
You must create the authwebhook-tls Secret (type kubernetes.io/tls) and patch the
MutatingWebhookConfiguration and ValidatingWebhookConfiguration with the CA bundle:

   CA_B64=$(kubectl get secret authwebhook-tls -n {{ .Release.Namespace }} \
     -o jsonpath='{.data.ca\.crt}' 2>/dev/null || \
     kubectl get configmap authwebhook-ca -n {{ .Release.Namespace }} \
     -o go-template='{{"{{"}}.data.ca\.crt{{"}}"}}' | base64 | tr -d '\n')

   kubectl patch mutatingwebhookconfigurations authwebhook-mutating --type=json \
     -p "[{\"op\":\"add\",\"path\":\"/webhooks/0/clientConfig/caBundle\",\"value\":\"${CA_B64}\"}]"

You must also create the datastorage-signing-cert Secret (type kubernetes.io/tls,
RSA 2048 key) for DataStorage's AU-9 audit-signing key -- DataStorage fails to
start without it, with no fallback (#334):

   openssl genrsa -out /tmp/signing-tls.key 2048
   openssl req -new -x509 -days 365 -key /tmp/signing-tls.key \
     -out /tmp/signing-tls.crt -subj "/CN=datastorage-signing-cert"
   kubectl create secret tls datastorage-signing-cert \
     --cert=/tmp/signing-tls.crt --key=/tmp/signing-tls.key -n {{ .Release.Namespace }}

You must also create gateway-tls, datastorage-tls, kubernautagent-tls, valkey-tls
Secrets (type kubernetes.io/tls) plus an inter-service-ca ConfigMap (key ca.crt)
for inter-service mTLS -- DD-PLATFORM-001. Without these, inter-service traffic
silently falls back to plain HTTP (SC-8 gap), and Valkey (TLS-only, DD-PLATFORM-006
Decision Area 8) will refuse all connections. See the chart README's
"Inter-service mTLS prerequisite" section for full openssl commands.
{{- end }}

=== Uninstalling ===

   helm uninstall {{ .Release.Name }} -n {{ .Release.Namespace }}

IMPORTANT -- Data Retention:
  - PostgreSQL and Valkey PVCs are RETAINED after uninstall (helm.sh/resource-policy: keep).
    To remove them manually:

      kubectl delete pvc postgresql-data valkey-data -n {{ .Release.Namespace }}

  - CRDs and their data are NOT removed. To delete all Kubernaut CRDs:

      kubectl delete crd $(kubectl get crd -o name | grep kubernaut.ai)

  - The {{ include "kubernaut.workflowNamespace" . }} namespace may contain active Jobs or PipelineRuns.
    Verify it is empty or clean up before uninstalling if it gets stuck:

      kubectl get jobs -n {{ include "kubernaut.workflowNamespace" . }}

=== Known Limitations ===

  - Single installation per cluster: cluster-scoped resources (ClusterRoles,
    WebhookConfigurations) use static names and will conflict if multiple
    releases are installed in different namespaces.
